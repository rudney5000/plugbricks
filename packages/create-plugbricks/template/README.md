# {{name}}

A platform managed by [plugbricks](https://github.com/rudney5000/plugbricks): you describe
which **bricks** you want (a database, your own services, …) and plugbricks keeps track of
them and of what they need from each other.

## What is in this folder

| Path | What it is | Commit it? | Edit it by hand? |
|---|---|---|---|
| `platform.json` | **What you want**: the list of installed bricks and where each came from, and the port of the GraphQL router (`router.port`, 4000 by default; you may change it). | yes | only `router.port`; use `plugbricks add` / `remove` for the bricks |
| `platform.lock` | **What plugbricks resolved**: exact versions, a fingerprint of every brick, which brick provides which capability, the volumes kept after a removal, and the volumes waiting to be deleted (deleted only when you ask for it explicitly). | yes | never |
| `.platform/bricks/` | A **copy of every installed brick**, so the project does not depend on where a brick came from. `plugbricks status` warns if a copy was changed. | yes | never |
| `bricks/` | **Bricks ready to add by name**: `npx plugbricks add postgres` adds `bricks/postgres`. It comes with `postgres` (provides `database`), `rabbitmq` and `nats` (each provides `queue`), whose images are public. Put any brick you want to add by name here; the folder name must be the brick's `name`. | yes | yes, add your own |
| `services/` | **The code of your own services**, one folder per brick that `npx plugbricks create` wrote: its source, its dependencies and its image recipe (`Dockerfile`). The brick itself is in `bricks/`. See `services/README.md`. | yes | yes, this is your code |
| `config/` | **Your non-secret settings** that services read. | yes | yes |
| `.generated/` | Files **produced by plugbricks** (`compose/compose.yaml`, `k8s/*.yaml`) by `plugbricks generate` and `up`. Always rebuilt from the files above. | no (ignored) | never |
| `.secrets/` | **Passwords** generated by plugbricks (`secrets.env`). Restricted to your user (mode 700 on Linux and macOS, an ACL on Windows); plugbricks refuses to write a secret if anyone else can read the folder (`SECRETS_NOT_RESTRICTED`). Kept when you remove a brick. | **never** (ignored) | no |
| `.gitattributes` | Keeps LF line endings on every OS, so brick scripts still run in Linux containers. | yes | rarely |
| `package.json` | Installs the `plugbricks` command for this project. | yes | rarely |

## First steps

A project made with a starter (`npm create plugbricks <name> -- --starter demo`) already has its
bricks added: `npm install`, then `npx plugbricks up`, and the generator printed where it answers.

```bash
npm install                 # installs the plugbricks command locally
npx plugbricks status       # what is installed: nothing yet, unless the project was made with a starter
```

A name adds the brick of `bricks/`; a path (with a `/`) adds any brick folder.

```bash
npx plugbricks add postgres                   # bricks/postgres, provides "database"
npx plugbricks create inventory --kind api    # your first API: bricks/inventory-api and services/inventory-api
npx plugbricks status
```

`create` writes a GraphQL subgraph that answers `{ inventoryItems { id name } }`, adds it, and
prints the command that builds its image; `--kind web` writes a web page instead. Build the image,
then start the platform:

```bash
docker build -t {{name}}/inventory-api:0.1.0 -f services/inventory-api/Dockerfile .
npx plugbricks up
```

A brick that requires something `bricks/` provides gets it proposed when you add it:
`add` asks before adding it (`--yes` adds it without asking, for a script). For a brick folder
next to you, write it as a path: `npx plugbricks add ./my-brick`.

What plugbricks refuses, and why:

- adding a brick whose required capability no installed brick provides;
- adding a second brick with the same name, or a second provider of the same capability;
- removing a brick that another brick still needs.

Every refusal prints a stable code such as `error REQUIRED_CAPABILITY_MISSING: …`.

Start and stop the platform:

```bash
npx plugbricks doctor                   # what up needs (Docker, ports, images), and what to fix first
npx plugbricks up                       # Docker Compose (needs Docker with Compose v2)
npx plugbricks up --runtime k8s --context my-cluster   # Kubernetes; you always name the cluster (add --kubeconfig <file> if needed)
npx plugbricks down                     # stops everything; your data and secrets are kept
```

If one of the bricks serves a GraphQL subgraph, `up` also starts a router in front of it. With Docker Compose it answers at `http://127.0.0.1:4000/graphql` (change the port with `router.port` in `platform.json`), and only from your own machine: nothing else is published.

`up` creates each service's database before the service starts and gives it its
`DATABASE_URL`. Removing a brick keeps its data; a volume declared `retention: delete` is
deleted only by `npx plugbricks up --prune-volumes`.
